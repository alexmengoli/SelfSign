# app-authentication: Optional shared-password application access
Scope: area:authentication
Status: ready
Base: new

## Goal
Optionally restrict access to SelfSign and its saved values, settings and signature images using one deployment-wide password, while preserving today's behavior when no password is configured. Keep browsers unlocked across visits and container restarts until access is revoked. This is access control, not encryption of the Docker volume or HTTP traffic; accounts, roles, password recovery and built-in TLS are excluded.

## Requirements
- R1: The server reads optional runtime environment variable `APP_PASSWORD`. An unset or empty value disables authentication: the existing workspace opens directly and existing API clients continue working without credentials. A nonempty value enables authentication without rebuilding the image. `docker-compose.yml` includes an optional, empty-by-default configuration example allowing the operator to set the password directly or through environment substitution. The password is never embedded in frontend assets, returned by an API, placed in URLs or logged.
- R2: With authentication enabled and no valid session, the initial page shows an application unlock screen rather than the usable workspace or saved data. It has an accessible password input, `Unlock` action, submitting state and generic `Incorrect password` feedback. Enter submits; failed attempts leave the app locked; connectivity/server failures show a retryable error without pretending the password is wrong. Loading authentication status must not briefly expose the workspace or start saved-data requests. Follow existing English UI, bundled fonts, Material controls, theme and SelfSign branding rules; support keyboard navigation and 360px-wide layouts.
- R3: A correct password creates a cryptographically random session represented by an opaque persistent `HttpOnly`, `SameSite=Strict`, path `/` cookie; use `Secure` under HTTPS with explicitly configured trusted proxy handling, never by blindly trusting client-supplied forwarding headers. All subsequent same-origin API requests and image loads authenticate with this cookie; the shared password is not resent for ordinary operations and no authentication credential is stored in localStorage or sessionStorage. The authenticated workspace loads saved data normally.
- R4: Sessions have no application-imposed absolute or inactivity timeout. Persist session validation state under `DATA_DIR` so the same browser remains unlocked after reload, closing/reopening the browser, and container recreation or updates using the same volume and password. Use a long-lived cookie within browser limits and renew it during authenticated use. Document that browser expiry, eviction or clearing site data can still require unlocking; do not promise an infinite browser cookie. Persist only a digest of the session token, not its raw bearer value.
- R5: Changing `APP_PASSWORD` and restarting the server revokes all previously issued sessions, even if a previously used password is later restored. Starting with authentication disabled also invalidates existing sessions before a later re-enable. Store sufficient protected configuration-generation metadata in `DATA_DIR` to detect these transitions without persisting the plaintext password. An operator must restart/recreate the service to apply an environment change; changing an environment variable is not live configuration.
- R6: While authenticated, expose an accessible `Lock` action with an English tooltip/name and a suitable local icon. It revokes the current server session, clears its cookie and returns to the unlock screen, without revoking other independent browser sessions. Tabs sharing the revoked cookie must relock on their next authentication check or protected request. When authentication is disabled, do not show `Lock`. A missing, invalid or revoked session during use returns the UI to the locked state and removes saved data from the rendered workspace; do not automatically retry failed writes after unlocking.
- R7: Enforce authentication centrally on the server for every existing and future `/api` route except explicitly public health and authentication bootstrap/login routes. Without a valid session, reads and writes return `401` without data or side effects, including direct `/api/images/:id` access, multipart uploads and settings updates. `GET /api/health` remains public with its existing response for Docker health checks. Public static assets and SPA HTML may load the unlock UI but never expose saved data or secrets. Sensitive API and authentication responses use `Cache-Control: no-store`; protected images must not remain reusable through HTTP caching after revocation.
- R8: Protect login and state-changing authenticated requests against cross-site request forgery, including multipart uploads, using maintained Fastify-compatible security tooling where suitable. Permit legitimate same-origin requests over supported HTTP and HTTPS deployments, but reject cross-origin attempts before side effects. Password comparisons must not leak matching prefixes. Limit login attempts to five failed attempts per client IP per minute, then return `429` with `Retry-After`; expire limiter entries and do not permanently lock out the deployment. Proxy trust must be explicit so forwarded IP headers cannot bypass throttling.
- R9: Plain HTTP on a trusted local network remains supported, including when a password is set. Documentation clearly states that authentication alone does not encrypt passwords, cookies or application data in transit; use an HTTPS reverse proxy for untrusted networks. It also states that anyone able to read the Compose configuration/environment or Docker volume is outside this protection boundary. No PDF bytes are sent to the server or external services, and no existing data format or saved-value behavior changes are required.
- R10: Update the root deployment/security documentation with `APP_PASSWORD`, disabled and enabled examples, persistent-session behavior, `Lock`, password rotation/revocation, volume requirements, proxy trust and HTTPS guidance. The user explicitly approves superseding the authentication exclusion in `app-foundation` and its no-authentication-only security note: make the minimal coordinated updates to that spec's Goal and R9, preserving its other requirements and IDs. Do not modify the independent `pdf-export` change.

## Approach
The current access boundary is `apps/server/src/app.ts` and `apps/server/src/api.ts`; runtime configuration belongs to `apps/server/src/config.ts` and its startup wiring. Add a scoped authentication module and separate session metadata beneath `DATA_DIR`, leaving field storage unchanged. Register protection before API handlers so multipart requests and direct image requests cannot bypass it. Use established Fastify cookie/security plugins rather than custom cookie parsing. Keep explicit public-route exceptions small, preserve SPA/CSP behavior, and avoid using the shared password itself as a cookie or signing key.

Gate workspace initialization at the Angular app shell (`apps/web/src/app/app.*` and `app.config.ts`) through an authentication service and focused unlock UI. `sidebar/field-library.service.ts` already uses same-origin HttpClient requests and image URLs, which will carry cookies without query-string tokens. Handle authentication loss centrally without turning ordinary server failures into password failures. Coordinate documentation in `README.md`, `docker-compose.yml` and the approved references in `u-spec/specs/app-foundation.md` during implementation only.

Use the existing Vitest server injection tests and Angular tests for isolated behavior. Add one focused authentication Playwright suite that uses isolated server instances, ports and temporary data directories for enabled/disabled configurations and restart/rotation scenarios, without changing credentials or deleting shared data underneath parallel suites.
